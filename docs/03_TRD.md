# 카페 판매·손익·재고 관리 기술 요구사항 문서(TRD)

- 작성일: 2026-10-12
- 기준 문서: `docs/01_PRD.md`, `docs/02_FRD.md`
- 구현 참고: `design/_1`~`design/_5`의 HTML 및 읽을 수 있는 PNG, `design/artisanal_operations/DESIGN.md`
- 목적: 어떤 기술로 화면·계산·저장·검사·배포를 구현할지 정한다. TRD는 개발자가 구현 방법을 알 수 있는 기술 설계 문서다.
- 사용자 지시: 추천 선택지 A는 자동 선택한다. 이 문서의 기술 추천은 선택 완료로 기록하며 구매·계정 연결·실제 배포는 이번 문서 작성에 포함하지 않는다.
- 상태: 기술 구성 선택 완료. FRD에 선택지가 아직 완성되지 않은 계산·운영 정책은 미정으로 유지한다.

## 1. 범위와 결정 근거

### 1.1 유지할 요구사항

판매 입력 → 메뉴 수익성 확인 → 기간 손익·재료 잔량 확인 순서를 유지한다. 판매·비용 입력/수정/삭제, 재료 입고·폐기·실측 기록, 일·월 조회, 저장·백업·복원을 모두 구현한다. 메뉴에서 남는 금액에는 식재료비·포장비·결제수수료를 포함하고, 임차료·인건비 등의 운영비는 기간 전체 손익에서 따로 뺀다.

엑셀 양식·가져오기, 추가 기간 조회, 미래 예상 손익, 자동 부족 판정·발주 추천, 기준 자료 편집, 여러 사람·기기 공유는 1차에 넣지 않는다. 시안에만 있는 POS 연결·일마감 승인·세무 검증·CSV/엑셀 보고서·자동 백업·전체 리셋도 제외한다. 시안의 고정 숫자와 완료 메시지는 실제 구현으로 대체한다.

### 1.2 A 추천 자동 선택 기록

| 항목 | 선택한 A 추천안 | 이유와 영향 |
| --- | --- | --- |
| 메뉴·재료·가격 기준 | 첨부 데이터 사용 | 앞서 FRD 단계에서 제시한 A. 판매·레시피·초기재고의 ID 연결을 유지. 시안의 다른 메뉴·단가를 옮기지 않음 |
| 사용 환경 | 한 매장, 한 사람이 한 컴퓨터의 동일 브라우저 프로필에서 사용 | PRD 단계에서 제시한 A. 계정·서버 공유 기능 없이 4시간 목표에 집중 |
| 화면 기술 | React + TypeScript + Vite | 다섯 화면과 입력창을 공통 구성으로 만들고 입력값 종류를 개발 중 검사 |
| 운영 기록 저장 | IndexedDB + idb | 브라우저의 구조화 저장소에 기록별로 보관. 여러 기록을 한 번에 성공/취소 처리 |
| 백업 | 전체 내용 JSON 파일 | FRD의 추천. 기준 자료·정책까지 보전해 복원 가능 |
| 복원 | 검증 후 현재 기록 전체 대체 | FRD의 추천. 미정인 병합 규칙이나 중복 거래를 만들지 않음 |
| 코드 저장소 | GitHub 비공개 저장소 | 개발 코드·문서 공유를 제한. 실제 운영 기록·백업 파일은 올리지 않음 |
| 배포 | Vercel 정적 웹 배포, 실제 영업용은 Pro 기준 | 서버 운영을 줄이면서 상업용 배포 조건을 검토 |

사용자가 A 자동 선택을 지시한 이후의 결정이다. 이전 PRD·FRD에 남아 있는 '사용 환경·원본 기준·백업 형식 미정'은 이 표에서 해소한다. 기존 문서의 기능이나 계산식을 바꾼 것이 아니다. 원가 수정·실사 이후 과거 수정 등 추천이 확정되지 않은 정책까지 임의 선택하지 않는다.

## 2. 전체 구조와 기술 구성

### 2.1 어디에서 무엇을 하는가

1. **GitHub:** 프로그램 코드, 요구사항 문서, 가상 샘플, 검사 코드를 보관한다.
2. **Vercel:** GitHub 코드를 배포용 파일로 만들어 브라우저에 제공한다.
3. **사용자의 브라우저:** 입력 검사·계산·목록 조회를 수행하고, IndexedDB에 운영 기록을 저장한다.
4. **사용자의 백업 파일:** 저장 완료된 운영 기록과 기준 자료를 JSON으로 내려받는다. 복원할 때 브라우저 안에서 읽는다.

운영 기록을 받는 서버/API나 클라우드 데이터베이스를 1차에 만들지 않는다. GitHub에 코드를 올리거나 Vercel에 배포해도 사용자가 입력한 매장 기록이 자동 백업되는 것은 아니다. 다른 사람은 같은 사이트를 열어도 자신의 브라우저 저장공간만 사용한다.

브라우저 저장은 사이트 주소와 브라우저 프로필에 연결된다. 미리보기 주소·실제 배포 주소·새 도메인의 기록이 자동 공유되지 않는다. 코드 업데이트는 같은 실제 운영 주소에서 진행하며, 주소 변경은 기존 주소에서 백업 후 새 주소에서 복원한다. [MDN 저장소 설명](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

### 2.2 선택 기술

| 역할 | 기술 | 쉬운 설명 / 구현 책임 |
| --- | --- | --- |
| 화면 | React | 목록·입력창·합계 표시를 재사용 가능한 조각으로 구성 |
| 개발 언어 | TypeScript, 엄격한 타입 검사 | 날짜·수량·채널 등 값의 종류가 잘못 연결되는 개발 실수를 줄임 |
| 개발·배포 파일 생성 | Vite | 개발용 실행과 배포용 파일 생성. Vercel이 지원하는 구성 |
| 디자인 | 일반 CSS와 공통 CSS 변수 | 시안의 색·간격·글자·표·입력창 규칙을 공통 적용. 실행 중 Tailwind CDN 사용 안 함 |
| 상태 | React Context + reducer 및 화면별 입력 상태 | 선택 기간과 저장된 데이터 버전을 공유하고, 입력 중 값은 저장 기록과 분리 |
| 저장 | IndexedDB, idb | 기록별 저장·조회·일괄 복원. 거래 전체 완료를 기다린 뒤 성공 표시 |
| 입력·파일 검사 | Zod + 별도 관계 검사 | 파일 모양·필수값을 검사하고, 메뉴ID·재료ID 연결도 확인 |
| 금액·수량 계산 | decimal.js | 소수 계산에서 이진 소수 오차를 줄임. 반올림 정책 자체를 바꾸지는 않음 |
| 검사 | Vitest, fake-indexeddb, 실제 브라우저 검사 | 계산·저장 실패·복원 불일치를 검사. 실제 브라우저 저장도 별도로 확인 |
| 코드 보관·배포 | GitHub + Vercel | 변경 이력 보관, 배포 미리보기, 운영 배포 |

React 구성·Vite 배포·idb 저장 완료 처리·Zod 검사·decimal.js 계산·Vitest 검사 방식은 각 공식 문서를 따른다. [React](https://react.dev/learn), [Vercel의 Vite 안내](https://vercel.com/docs/frameworks/frontend/vite), [idb](https://github.com/jakearchibald/idb), [Zod](https://zod.dev/), [decimal.js](https://mikemcl.github.io/decimal.js/), [Vitest](https://vitest.dev/guide/)

패키지는 구현 시점에 서로 호환되는 안정 버전을 설치하고 `package-lock.json`으로 고정한다. '항상 최신'으로 자동 갱신하지 않는다. Node.js는 개발·Vercel 빌드에서 동일한 지원 LTS 버전을 사용하고 `package.json`의 `engines`와 Vercel 설정에 기록한다. 정확한 버전은 프로젝트 생성 시 검증한다. Vite 안내의 현재 최소 요구는 Node.js 20.19+ 또는 22.12+이며, 이를 장기 운영 버전 추천과 혼동하지 않는다. [Vite 설치 조건](https://vite.dev/guide/)

위 위치는 개발 구조이지 사용자에게 새 메뉴를 제공하는 기능이 아니다. 화면 코드는 계산식이나 저장 규칙을 직접 갖지 않고 공통 계산·저장 기능을 호출한다.

- 화면 전환은 한 웹페이지 안에서 처리한다. 별도 라우터 패키지·페이지별 서버 경로를 도입하지 않아도 다섯 화면을 사용할 수 있다.
- 시안 HTML은 참고 구조로 옮기며 고정 표와 예시 숫자를 실제 조회 결과로 대체한다. `#` 링크·시연용 완료 알림만 복사하지 않는다.
- 판매 수정·삭제는 시안에 없어도 FRD 필수 기능으로 구현한다. 입력창에서 날짜·메뉴·재료를 실제로 선택할 수 있게 한다.
- 공통 디자인 값은 시안 HTML의 테마와 DESIGN.md 상단 정의를 기준으로 CSS 변수로 정리한다. 상충하는 설명 문구는 기능 정책 근거로 사용하지 않는다.
- 현재 브라우저에서 사용할 수 있는 기본 글꼴을 우선하고, 외부 Google Fonts·원격 프로필 사진·광고 이미지 요청을 제거한다. 장식 이미지가 꼭 필요하면 권리 확인된 파일만 자체 배포한다.
- 입력창의 제목·입력 설명·버튼 용도를 읽을 수 있게 하고 키보드로 입력·취소·확인할 수 있게 한다. 단위와 오류를 색상만으로 구분하지 않는다.
- `design/_4/screen.png`는 읽을 수 없어 대시보드는 HTML 기준으로 구현·검사한다. 읽을 수 있는 나머지 PNG를 배치 참고로 사용한다.

## 4. 기록 형식과 데이터베이스

### 4.1 자료의 표현

- 원본의 ID와 연결 관계를 유지한다. 이름으로 기록을 연결하지 않는다.
- 날짜는 `YYYY-MM-DD`, 월은 `YYYY-MM`로 보관한다. 영업일을 UTC 자정 시각으로 바꾸지 않아 날짜가 하루 밀리는 오류를 피한다.
- 백업 생성 시각은 ISO 8601의 UTC 시각으로 보관하고, 화면·파일명에는 한국 시간으로 표시한다. 실제 영업일과 백업 시각을 구분한다.
- 원본의 없는 선택 항목은 내부에서 `null`로 표현하며 0·빈 문자열과 구분한다. 단, 레시피의 빈 적용채널은 '모든 채널'이라는 의미를 유지한다.
- 채널은 원본의 `매장`·`포장`으로 통일한다. 시안의 `dine_in`·`takeout`은 입력 연결 단계에서만 대응한다.
- 새 기록ID는 `crypto.randomUUID()`로 만든다. 기존 S/E/X ID와 충돌하지 않게 하고 수정 시 같은 ID를 유지한다.
- 금액·수량 소수는 내부 계산용 십진 문자열과 decimal.js로 처리한다. 샘플 숫자는 읽을 때 한 번 정규화하며 원본의 의미와 값을 유지한다. `NaN`·무한대·안전하지 않은 정밀도 손실은 허용하지 않는다.

### 4.2 IndexedDB 구조

DB 이름은 `prep-cafe-operations`, 저장 구조 버전은 최초 `1`로 시작한다. 데이터 출처의 버전·백업 형식 버전·계산 정책 버전과 구분한다.

| 저장 구역 | 키 | 보관 항목 / 주요 조회 기준 |
| --- | --- | --- |
| `appMeta` | 고정 키 `state` | 초기화 완료, 데이터 출처, 저장 구조·정책 버전, 전체 변경번호 |
| `suppliers` | supplier_id | 공급사 기준 자료 |
| `materials` | material_id | 단위·구매용량·기초 가격·납기·안전재고 일수 등 원본 항목 |
| `menus` | menu_id | 이름·기준가·분류·레시피 버전 |
| `recipes` | 내부 복합 키 | 버전·메뉴·재료·채널 연결. 원본에 없는 행 ID는 복합 키로 구성 |
| `priceHistory` | material_id + effective_date | 적용 시작일·구매가격·구매용량 |
| `calendar` | date | 영업·마감 상태·원본 메모 |
| `openingInventory` | material_id + date | 초기 수량·단위 |
| `sales` | sale_id | 원본 판매 항목. date, menu_id, date/menu_id/channel 조회 인덱스 |
| `inventoryEvents` | event_id | 입고·폐기·실사 항목. date, material_id/date 조회 인덱스 |
| `expenses` | expense_id | 귀속일·항목·금액·기록 기준. date, category/date 조회 인덱스 |
| `monthlyExpensePlan` | month + category | 원본 월 계획. 실제 비용에 자동 합산하지 않음 |
| `policies` | policy key | 확정한 운영 기준과 버전. 미정 값은 명시적으로 미정 상태 보관 |

인덱스는 기록을 빠르게 찾는 보조 목차다. 날짜·메뉴·채널 인덱스는 중복 확인에 쓰되, FRD의 미정 중복 정책을 기술적으로 자동 합산/덮어쓰기 정책으로 확정하지 않는다. 기록 간 참조는 저장 전 검사한다. IndexedDB가 메뉴ID 연결을 자동 검증해 주는 것으로 가정하지 않는다.

합계·잔량은 원본에서 계산되는 결과이므로 별도 확정 기록처럼 저장하지 않는다. 메모리 캐시만 사용하고 기록 변경·복원·정책 변경 시 폐기한다. 실제 센 수량·당시 원가·수수료는 다시 만들 수 없는 원본 정보이므로 보관한다.

## 5. 시작 자료와 가져오기

### 5.1 첫 실행 — F01

1. 저장소 지원 여부를 확인하고 DB를 연다.
2. 초기화 완료 기록이 있으면 기존 운영 자료를 읽는다. 샘플을 추가하지 않는다.
3. 최초 실행이면 `public/sample/store-operations.json` 한 파일을 읽는다. 제공 JSON을 초기 샘플용으로 변환하며 엑셀을 동시에 가져오지 않는다.
4. Zod 검사와 관계 검사로 개수·ID·단위·날짜·메뉴/재료 연결을 확인한다.
5. 검사 완료된 자료와 초기화 완료 표시를 한 트랜잭션에 저장한다. 트랜잭션은 '모두 성공하거나 모두 취소되는 묶음'이다.
6. 완료 후 조회 결과를 만든다. 실패하면 초기화 완료로 표시하지 않는다.

샘플 다운로드 실패는 재시도 안내. 기존 DB 읽기 실패는 샘플로 덮어쓰지 않는다. 사용자가 사이트 데이터를 전부 지운 경우에는 과거 사용 여부도 지워질 수 있으므로 이를 자동 감지·복구한다고 약속하지 않는다. 새 저장공간임을 표시하고 샘플·백업 복원의 의미를 설명한다.

### 5.2 사용자 파일 가져오기

1차 사용자가 직접 가져오는 파일은 **프로그램 백업 복원 파일**뿐이다. 엑셀·CSV·원본 JSON을 범용 가져오는 메뉴나 변환 기능은 추가하지 않는다. 원본 JSON은 초기 개발 자료, 백업 JSON은 명시된 백업 형식이다. 두 파일이 JSON이라는 이유만으로 동일하게 복원하지 않는다.

2차 엑셀 양식·가져오기용 라이브러리를 지금 설치하지 않는다. 이후 도입 시 행별 오류·중복·단위·날짜 변환을 별도 FRD에 정의하고, 현재 입력 검사·저장 계층을 재사용한다.

## 6. 입력·계산·저장 연결

### 6.1 공통 저장 순서 — F03~F05, F07~F11, F14

입력 중 상태 → 입력·관계 검사 → 합의된 정책으로 미리 계산 → 저장 버튼 → DB 변경번호 확인 → 기록 변경과 변경번호 증가를 같은 쓰기 트랜잭션으로 적용 → `tx.done` 완료 대기 → 캐시 폐기·조회 갱신 → 완료 표시.

- 입력 미리보기는 메모리에서만 계산하며 DB에 저장하지 않는다. 취소·닫기는 거래를 만들지 않는다.
- 저장 중에는 같은 요청을 반복 제출하지 않게 한다. 새 ID는 요청마다 반복 생성하지 않고 해당 저장 시도에 유지한다.
- 기존 기록을 읽을 때 얻은 변경번호와 DB의 번호가 다르면 저장하지 않고 새 자료를 확인하게 한다. 여러 탭도 같은 쓰기 트랜잭션 안에서 검사해 뒤늦은 덮어쓰기를 방지한다.
- 판매 삭제로 재고를 별도 증가 기록에 남기지 않는다. 판매를 수정/제외하고 잔량을 다시 계산해 이중 반영을 피한다.
- 저장 트랜잭션 실패는 기존 기록 유지. **저장은 완료됐지만 화면 갱신만 실패한 경우**에는 '저장은 완료, 화면 다시 읽기 필요'로 구분한다. 재시도 때문에 거래를 다시 추가하지 않는다.
- 브라우저를 닫을 때만 저장하는 방식은 사용하지 않는다. 저장마다 완료를 기다린다. 저장 완료도 갑작스러운 전원 차단에 대한 절대 보장이 아니므로 파일 백업을 별도로 제공한다. [IndexedDB 저장 안내](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB), [idb 완료 처리](https://github.com/jakearchibald/idb)

### 6.2 계산 계층 — F06·F12·F13

계산은 `src/domain/`의 화면에 의존하지 않는 함수로 구현한다. 같은 입력이면 어느 화면에서도 같은 결과가 나와야 한다. 함수는 값 외에 `complete / incomplete / unavailable` 상태와 누락 이유를 반환한다.

| 영역 | 구현할 FRD 계산을 유지하는 방법 |
| --- | --- |
| 판매 | 순매출 = 수량 × 당시 단가 − 총 할인. 과거 순매출·원가·수수료는 원본 기록 보전 |
| 메뉴 수익성 | 순매출 − 식재료·포장원가 − 결제수수료. 운영비를 메뉴에 배분하지 않음 |
| 메뉴 기간 비율 | 기간 남는 금액 합계 ÷ 기간 순매출 합계. 행별 비율 단순 평균 금지 |
| 기간 손익 | 순매출 − 판매원가 − 결제수수료 − 귀속일 기준 운영비. 월 계획·입고 구매액을 다시 더하지 않음 |
| 재료 사용 | 해당 판매의 레시피 버전·채널에 맞는 개당 사용량 × 판매수량 |
| 잔량 | 초기재고 + 누적 입고 + 누적 음수 폐기 + 누적 실사조정 − 누적 판매 사용 |
| 조회 기간 | 판매·비용은 선택 일/월 범위, 잔량은 초기 기준일부터 확인 기준일까지 누적 |

이는 FRD 6절의 계산을 구현하는 구조다. 아직 제안인 식·반올림을 이미 확정된 계산 기준으로 격상하지 않는다. 십진 계산 도구를 도입하더라도 원가 적용·실측 처리 정책은 바꾸지 않는다.

날짜 비교는 날짜 문자열 또는 명시적인 한국 날짜 유틸리티로 처리한다. 월은 해당 월 첫날 이상·다음 월 첫날 미만의 범위로 조회한다. 미래/미마감/자료 없음/판매 0 상태를 분리하고, 빈 자료를 0으로 만들어 완전한 월 실적처럼 표시하지 않는다.

### 6.3 미정 정책의 처리

FRD에서 미정인 새 판매수수료, 기존 판매 수정 시 원가 재적용, 직접 비용과 배분 비용의 관계, 실측 후 과거 수정, 같은 날 실사 순서, 마감 상태 변경, 0원 판매·환급·음수 잔량·필수 입력·반올림을 기술 기본값으로 정하지 않는다.

정책은 한곳의 설정 자료로 관리하고 버전과 함께 백업한다. 미정인 필수 정책을 필요로 하는 작업은 구현 완료로 인정하지 않으며, 필요한 기준을 명시한다. 이것은 영구적으로 기능을 빼는 결정이 아니다. 핵심 입력을 제한한 상태를 MVP 완료로 배포하지 않고 개발 전 추천안을 정리해 사용자의 A 자동 선택 지시에 따라 결정을 기록해야 한다. 추천이 명시되지 않은 FRD의 A/B 후보는 'A'라는 문자만 보고 자동 선택하지 않는다.

## 7. 백업과 복원

### 7.1 백업 파일 구조 — F15

JSON 최상위 항목은 다음과 같이 정한다. 기록 건수는 설명 정보이며 실제 배열을 대신하지 않는다.

| 항목 | 내용 |
| --- | --- |
| `format` | `prep-cafe-backup` 고정 식별값 |
| `backupVersion` | 최초 백업 형식 `1` |
| `exportedAt` | 백업 생성 시각 |
| `appVersion` | 파일을 만든 앱 버전 |
| `sourceMeta` | 샘플 출처·자료 기간·통화·금액 기준 |
| `policyVersion`, `policies` | 계산·운영 기준과 미정 상태 |
| `data` | suppliers, materials, menus, recipes, priceHistory, calendar, openingInventory, sales, inventoryEvents, expenses, monthlyExpensePlan의 11개 배열. 초기화 표시·캐시는 포함하지 않음 |
| `counts` | 각 배열의 기록 수. 내용과 일치하는지 검증 |

백업은 모든 구역을 하나의 읽기 트랜잭션으로 읽어 서로 같은 저장 시점의 자료를 만든다. 저장 중인 작업이 끝난 뒤 실행하고 미저장 입력은 포함하지 않는다고 안내한다. 직렬화 후 Blob·Object URL로 다운로드하고 사용이 끝난 URL을 해제한다. 파일명은 FRD 예시처럼 한국 시간의 날짜·시간을 포함한다. 다운로드를 요청했다는 사실과 실제 파일 보관 확인을 구분한다.

빈 운영 기록도 기준 자료를 보전한다. 비밀번호 암호화·서버 백업·자동 백업은 1차에 추가하지 않는다. JSON 백업은 읽을 수 있는 파일이므로 사용자 보관 위치에서 접근을 제한해야 한다.

### 7.2 복원 순서 — F16

**파일 선택 → 읽기·검사 → 검증 결과 표시 → 복원 시작 → 전체 대체 확인 → 실행/취소**라는 FRD 순서를 유지한다.

1. File API로 선택 파일을 브라우저 안에서 읽는다. 서버에 업로드하지 않는다.
2. `JSON.parse`와 Zod로 구조·형식 버전을 검사한다. 백업의 코드나 HTML은 실행하지 않는다.
3. 모든 ID의 유일성, 참조 연결, 단위, 날짜, 금액·수량 표현, 배열과 counts 일치, 정책 지원 여부를 검사한다.
4. 다른 매장·미지원 정책·버전은 대체 대상이 맞는지 검증한다. 1차는 프렙 카페 자료만 지원하므로 다른 매장 파일은 현재 기록을 바꾸지 않고 안내한다.
5. 화면에 실제 파일의 시점·매장·기간·기록 수·대체 범위를 표시한다. 시안의 8/11 숫자나 고정 파일명을 검증 결과로 사용하지 않는다.
6. 현재 데이터 백업을 안내한다. 취소는 변경 없음. 자동 백업 파일을 추가 생성하지 않는다.
7. 검증 완료된 전체 배열을 메모리에 준비한 뒤 모든 관련 저장 구역의 비우기·새 기록 넣기·정책 적용·변경번호 증가를 **하나의 쓰기 트랜잭션**으로 실행한다.
8. 완료 후 캐시를 버리고 데이터를 다시 읽는다. 기록 적용 실패는 트랜잭션 전체 취소, 화면 갱신 실패는 이미 저장된 복원을 다시 읽도록 안내한다.

파일 읽기·검사·사용자 확인은 쓰기 트랜잭션을 시작하기 전에 완료한다. 트랜잭션 안에서 파일 읽기나 네트워크 대기를 넣지 않는다. 저장 용량이 부족하면 기존 자료를 먼저 별도로 삭제해 공간을 확보하는 방식은 금지한다.

시안의 50MB는 정책 미정으로 유지한다. 개발 중 파일 메모리·처리시간 검사를 통해 상한 추천안을 별도 기록하고 선택 지시에 따라 반영한다. 검사하지 않은 임의의 파일을 '검증 완료'라 표시하거나 요약만 있는 파일을 복원하지 않는다.

### 7.3 구조 변경과 앱 되돌리기

DB 구조 버전 변경은 IndexedDB upgrade 트랜잭션으로 수행한다. 초기 1차는 복잡한 변환을 만들지 않는다. 이후 버전은 기존 자료를 새 구조로 옮기는 방법과 과거 백업 읽기 검사를 추가한다. 최신 DB/정책을 이해하지 못하는 구버전 앱은 저장·삭제를 중단하고 지원 버전으로 열도록 안내한다.

**Vercel 코드 롤백은 IndexedDB 기록을 되돌리지 않는다.** 데이터 복원은 사용자가 받은 백업 파일로 따로 수행한다. 배포 전에 구조 호환성과 백업·복원 검사를 수행한다.

## 8. 개인정보와 매장 정보 보호

- 고객 이름·전화번호·카드번호·계정 비밀번호를 다루는 기능을 만들지 않는다. 원본 공급사 정보와 재고 사유 등 기존 항목은 보전한다.
- 운영 기록·실측·비용·백업 내용을 GitHub, Vercel 요청, 분석 서비스, 오류 수집 서비스로 보내지 않는다. 오류 로그에 입력 전체나 파일 내용을 출력하지 않는다.
- Vercel에 공개되는 파일은 코드와 **가상 샘플**뿐이다. 비공개 GitHub 저장소여도 배포된 브라우저 코드·샘플 파일은 사이트 방문자가 읽을 수 있으므로 실제 기록을 빌드 파일에 넣지 않는다.
- 백업·실제 운영 Excel/JSON·`.env`·토큰·인증 파일은 Git 추적에서 제외한다. 필요한 공개 샘플만 명시적으로 포함하고 `.gitignore`는 이미 올라간 비밀을 지우지 않는다는 점을 배포 검사에 반영한다.
- 프런트 코드에 비밀키를 두지 않는다. `VITE_` 환경 변수는 사용자에게 전달될 수 있으므로 비밀 저장 장소로 사용하지 않는다. [Vite 환경 변수 안내](https://vite.dev/guide/env-and-mode)
- 복원한 메모·이름은 React 텍스트로 표시한다. `innerHTML`·`eval`로 실행하지 않는다. 파일에서 임의 URL·스크립트를 읽어 외부 요청하지 않는다.
- 외부 스크립트·광고·분석·원격 글꼴 요청을 제거한다. 자체 파일만 실행하도록 CSP(허용된 파일 출처 제한)를 설정하고 `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, 보수적 Referrer-Policy를 Vercel 헤더에 적용한다. 개발 중 필요한 설정과 실제 배포 설정은 구분한다.
- 운영 주소는 HTTPS로 접속한다. HTTPS는 통신 보호이며 브라우저 기록·백업 파일의 암호화를 의미하지 않는다.
- 앱 로그인·직원 권한·암호화 기능은 승인된 1차 범위에 없다. 따라서 같은 컴퓨터·프로필에 접근하는 사람은 기록을 볼 수 있다. 한 사람의 개인 브라우저 프로필과 운영체제 잠금을 사용한다.
- 실제 운영은 일반 브라우저 모드에서 한다. 시크릿 모드는 종료 시 저장 자료가 사라질 수 있고 브라우저 정리·저장공간 부족도 자료 손실 요인이므로 백업이 필요하다. 지원할 경우 `navigator.storage.persist()`로 지속 보관을 요청하되 승인·보존을 보장하지 않는다. [MDN 저장 제한](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- 기록을 보내지 않아도 Vercel의 파일 제공 과정에서 접속 IP 등 요청 정보가 처리될 수 있다. '외부에 어떤 정보도 나가지 않는다'고 표현하지 않는다.

GitHub는 비공개 저장소로 시작한다. Vercel 연동 접근은 이 프로젝트 저장소에 필요한 범위로 제한하고 개인 토큰을 코드에 보관하지 않는다. 비공개 저장소의 접근 범위는 GitHub 공식 안내에 따른다. [GitHub 저장소 안내](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)

## 9. 처리 속도와 용량

제공 JSON의 현재 파일 크기는 3,455,500바이트, Excel은 490,677바이트다. 운영 기록은 11,187줄(판매 6,112 + 재고 1,515 + 비용 3,560)이며 기준 자료는 별도다. 아래는 **구현 후 확인할 목표**이며 이미 측정한 성능이 아니다.

| 동작 | 목표 | 측정 조건 |
| --- | --- | --- |
| 초기 준비 | 5초 이내 | 샘플 수신 완료부터 검사·저장·첫 조회 완료. 네트워크 시간 별도 기록 |
| 일·월 조회 | 500ms 이내 | 현재 샘플, 지원 데스크톱 브라우저, 준비된 데이터 |
| 저장 후 결과 확인 | 1초 이내 | 입력 검사부터 저장 완료·수익성/손익/잔량 갱신 |
| 백업·복원 | 각각 5초 이내 | 현재 샘플 크기, 파일 읽기·내용 검사·처리 기준. 확인창 대기시간 제외 |

- 시작 시 한 번 읽은 기록을 메모리에 보관하고 날짜·메뉴·재료별 Map으로 연결한다. 화면을 그릴 때마다 샘플을 다시 다운로드하지 않는다.
- 가격이력은 재료별 날짜순, 레시피는 버전·메뉴·채널 기준으로 정리한다. 각 판매마다 전체 레시피·가격이력을 반복 탐색하지 않는다.
- 현재 규모에서는 한 번의 순회와 같은 결과 캐시를 우선한다. 기록 변경번호가 바뀌면 캐시를 폐기한다. 지속 저장된 합계가 원본과 어긋나는 구조를 만들지 않는다.
- 일·월 기간으로 목록을 좁힌다. 전체 6,112줄을 항상 화면에 동시에 만들지 않는다. FRD에 미확정인 필터·페이지 이동 기능을 임의 추가해 성능 문제를 해결하지 않는다.
- 백업 생성·복원 중에는 처리 중 상태를 보여준다. Worker·가상 스크롤·추가 서버는 목표 미달이 확인될 때 같은 기능을 유지하는 기술 최적화로 검토한다.
- DB에 보관할 공간은 브라우저가 결정한다. `navigator.storage.estimate()`는 참고값으로만 사용하고 저장 실패를 실제 처리한다. 용량을 확정 보장하지 않는다.

## 12. GitHub 보관과 Vercel 배포

1. 프로젝트에 코드·문서·패키지 버전 고정 파일·가상 샘플·검사를 준비한다. 실제 운영 파일과 토큰은 제외한다.
2. 개발 명령은 `npm run dev`, 검사 명령은 `npm run typecheck`, `npm run test`, `npm run build`로 통일한다. `build`는 타입 검사와 Vite 빌드를 수행하도록 설정한다.
3. GitHub 비공개 저장소에 커밋한다. 기본 배포 브랜치는 `main`으로 정하고 저장소명·소유 계정은 실제 작업 시 사용자 계정에서 확인한다.
4. Vercel에서 해당 저장소를 연결한다. Framework는 Vite, 빌드 명령은 `npm run build`, 출력 폴더는 `dist`, 프로젝트 루트는 저장소 루트로 설정한다.
5. PR/작업 브랜치 미리보기에는 가상 기록만 사용한다. 실제 운영 기록을 검사를 위해 업로드하지 않는다.
6. 검사 후 `main` 배포를 운영 주소로 사용한다. 클라이언트 상태로 화면 전환하므로 `/sales` 등 서버 경로를 따로 만들지 않는다.
7. HTTPS·응답 보안 헤더·운영 주소·처음 열기·기록 보관·재접속·백업·복원을 실제 브라우저에서 확인한다.
8. 배포 실패는 빌드/타입 오류를 해결하고 기존 정상 배포를 유지한다. 코드 롤백 전에 저장 구조 호환성을 확인한다.

정적 웹 배포 설정과 Git 연결에 따른 미리보기는 Vercel 공식 Vite 안내를 따른다. [Vercel Vite 배포](https://vercel.com/docs/frameworks/frontend/vite)

프로그램 파일 제공에는 네트워크가 필요하다. 인터넷이 끊겨도 열린 화면에서 모든 사용을 보장하는 기능이나 설치형 PWA는 1차에 추가하지 않는다. 연결 실패가 브라우저 기록 삭제로 이어져서는 안 된다.

- 동일 데이터에서 메뉴별 남는 금액 합계와 기간 운영비를 통한 손익이 대시보드 손익과 일치해야 한다. 과거 원본과 새 계산의 불일치를 무조건 원본 수정으로 해결하지 않는다.
- 4개 PNG와 대시보드 HTML을 참고해 필수 버튼·입력·오류 메시지·단위가 보이고 작동하는지 확인한다. 제외 기능이 동작하는 버튼으로 남지 않아야 한다.

## 14. 4시간 목표와 완료 판단

PRD의 기획 25분·화면 설계 20분·개발 140분·검사 35분·배포 20분, 총 240분 계획을 유지한다. 문서 세 개를 작성한 실제 누적 시간은 측정되지 않았으므로 이후 개발에 새로 4시간이 남았다고 가정하지 않는다. 작업 시작 시 남은 시간을 확인한다.

4시간을 위해 서버·로그인·공유·범용 가져오기·보고서·자동 알림을 추가하지 않고 동일 계산·입력창·확인창을 재사용한다. 검사와 배포 시간을 없애서 미정 정책을 덮거나 필수 기능을 줄이지 않는다.

완료는 PRD M01~M08 및 FRD F01~F16의 핵심 흐름이 실제 배포 주소에서 동작하고, 보관·복원 검사와 타입 검사·계산 검사가 통과한 상태다. **핵심 계산에 필요한 운영 정책이 미정이거나 필수 입력을 막아 둔 상태는 완료가 아니다.** 기능을 변경해야 하면 TRD만 고쳐 몰래 범위를 바꾸지 않고 PRD·FRD 결정 기록에 사용자 선택 근거를 남긴다.

이번 산출물은 기술 설계 문서다. 코드 생성·GitHub 업로드·Vercel 프로젝트 생성·구매·배포를 실행했다는 뜻은 아니다.

## 15. EPIC 1 구현 기록
