## 1. 전체 작업 순서와 나눈 이유

**작업 순서는 판매·수익성 → 재고·백업 → 비용·전체 손익·복원이다. 총 3개 EPIC, 14개 Story로 구성한다.**

EPIC은 함께 완성할 작업 묶음이고, User Story는 사용자가 한 가지 목적을 달성하는 기능이다. 등록·수정·삭제는 각각 별도 Story로 나눈다.

| 순서 | EPIC | Story 수 | 끝나면 화면에서 확인할 결과 |
| --- | --- | ---: | --- |
| 1 | 판매 기록과 메뉴 수익성 | 4 | 판매를 등록·수정·삭제하고 메뉴에서 남는 금액 확인 |
| 2 | 재료 잔량과 기록 백업 | 5 | 판매 소진·입고·폐기·실측을 반영한 잔량 확인, 백업 파일 받기 |
| 3 | 비용과 전체 손익, 기록 복원 | 5 | 비용을 관리하고 기간 손익 확인, 백업 시점으로 복원 |
| **합계** | **3개 EPIC** | **14** | **핵심 흐름 전체 완성** |

판매가 메뉴 수익성과 재료 사용량의 출발점이므로 먼저 만든다. 다음으로 재고 연결을 확인하고 기록을 백업할 수 있게 한다. 마지막으로 비용을 연결해 전체 손익을 완성하고, 변경된 기록까지 복원되는지 검사한다.

각 Story에는 실제 저장과 필요한 계산·오류 처리를 포함한다. 공통 저장소나 화면 틀은 이를 지원하는 개발 작업으로 처리하며, 별도의 사용자 Story로 늘리지 않는다.

## 2. 개발 전 준비와 공통 완료 조건

FRD에 남아 있는 수수료 입력 방식, 과거 판매 수정 시 원가, 실측 이후 과거 수정, 비용의 추가·대체 관계, 마감·반올림 기준은 **관련 Story 착수 전에 정리한다.** 추천안 A는 자동 선택하되 선택 근거를 기록하고, 기존에 확정한 계산 기준은 바꾸지 않는다.

모든 Story에 다음 조건을 적용한다.

- 저장한 기록은 브라우저를 닫았다가 다시 열어도 남아야 한다.
- 입력 오류·저장 실패는 이유를 표시하며 기존 기록을 보존해야 한다.
- 취소는 기록을 바꾸지 않고, 버튼을 반복 눌러도 중복 반영하지 않아야 한다.
- 자동 검사는 작은 가상 자료의 기대값과 비교한다. 시안의 숫자를 정답으로 쓰지 않는다.
- 미정 정책, 가짜 완료 메시지, 저장되지 않는 화면만으로 완료 처리하지 않는다.

## 3. EPIC 1 — 판매 기록과 메뉴 수익성

**포함 Story: S1.1~S1.4, 총 4개**

제공 자료의 최초 준비, 공통 입력 검사·저장, 날짜·월 선택을 이 EPIC의 기반 작업으로 구현한다. 새로 열 때 샘플을 중복 추가하지 않는다.

| Story | 사용자가 할 수 있는 일 | 자동 검사 | 화면에서 확인할 행동과 예상 결과 |
| --- | --- | --- | --- |
| **S1.1 판매 등록** | 날짜·메뉴·채널·수량·단가·할인·수수료를 기록한다. | 순매출·원가·수수료 계산, 포장 전용 재료 적용, 필수값 누락·중복·저장 실패 검사. | 미등록 조합으로 판매를 입력하고 저장한다. 목록에 한 번만 나타나며, 다시 열어도 남는다. 잘못된 수량은 오류를 표시한다. |
| **S1.2 판매 수정** | 잘못 입력한 판매를 고친다. | 기존 기록을 새 값으로 대체하는지, 날짜·메뉴·채널 변경 시 이전·새 대상의 계산이 바뀌는지 검사. | 기존 판매 수량을 늘려 저장한다. 같은 기록의 수량·금액이 바뀌고 별도 판매가 추가되지 않는다. |
| **S1.3 판매 삭제** | 잘못된 판매 기록을 제거한다. | 삭제 대상만 제외되는지, 취소·실패 시 원본이 유지되는지 검사. 재료 사용량 계산에서도 해당 판매를 제외한다. | 삭제를 취소하면 행이 남고, 확정하면 사라진다. 다시 열어도 삭제 결과가 유지된다. |
| **S1.4 메뉴 수익성 확인** | 선택한 일·월에 메뉴별로 얼마나 남았는지 확인한다. | 재료·포장·결제수수료 포함, 기간 합계 기준 비율, 매출 0·원가 누락 처리 검사. | 일·월을 바꾸어 메뉴 결과를 본다. 판매 수정·삭제가 반영되며, 운영비를 빼기 전 금액이라는 설명이 보인다. |

### 완료 기준

판매 화면에서 실제 기록 관리와 일·월 메뉴 수익성 확인이 가능하다. 원본 메뉴·가격을 사용하고, 판매 수정·삭제가 계산에 반영된다. 재료 사용량의 공통 계산도 검사하며, 잔량 화면에서의 확인은 EPIC 2에서 이어간다.

## 4. EPIC 2 — 재료 잔량과 기록 백업

**포함 Story: S2.1~S2.5, 총 5개**

EPIC 1의 판매 기록·레시피·저장 기능을 이어받는다. 입고·폐기·실측을 만든 뒤, 판매 변경까지 포함한 잔량을 확인한다.

| Story | 사용자가 할 수 있는 일 | 자동 검사 | 화면에서 확인할 행동과 예상 결과 |
| --- | --- | --- | --- |
| **S2.1 입고 기록** | 들어온 재료의 수량을 기록한다. | 재료·단위·수량 검사, 입고 증가 처리, 저장 실패 시 원본 유지 검사. | 우유 입고량을 저장한다. 입고 기록과 기준일 이후 잔량이 증가하고 다시 열어도 유지된다. |
| **S2.2 폐기 기록** | 버린 재료의 수량을 기록한다. | 폐기 감소 처리, 원본 음수 폐기의 이중 부호 오류, 잘못된 수량 검사. | 우유 폐기를 저장한다. 잔량이 폐기량만큼 감소한다. 판매 사용량에는 같은 폐기가 추가되지 않는다. |
| **S2.3 실제 재고 기록** | 실제로 센 수량을 기록해 장부와의 차이를 확인한다. | 실측수량·조정량 분리, 실측 0과 빈칸 구분, 합의한 실사 순서·과거 수정 정책 검사. | 실제 센 수량을 입력한다. 기록 잔량·실측수량·차이가 구분되어 보이고, 저장 후 합의한 기준으로 반영된다. |
| **S2.4 재료 잔량 확인** | 선택한 기준일까지 남은 재료를 확인한다. | 초기재고부터 누적 계산, 포장재 적용, 판매 등록·수정·삭제 연동, 월말 잔량·자료 누락 검사. | 아메리카노 판매 수량을 1 늘리고 잔량을 확인한다. 적용 레시피만큼 원두 사용량이 늘어난다. 월 조회는 일별 잔량의 합계가 아닌 기준일 잔량을 보여준다. |
| **S2.5 전체 기록 백업** | 현재 저장된 기록을 파일로 보관한다. | 판매·비용·재고·기준 자료·정책의 전체 포함, 건수 일치, 같은 저장 시점, 생성 실패 검사. | 백업 버튼을 누른다. 실제 JSON 파일이 내려받아지고 생성 시점·포함 기록 수가 표시된다. 건수 요약만 있는 파일이 아니어야 한다. |

### 완료 기준

재고 화면에서 입고·폐기·실측과 판매 소진을 함께 반영한 잔량을 확인할 수 있다. 과거 판매 변경도 합의한 실측 정책에 따라 반영된다. 백업에는 아직 수정하지 않은 제공 비용기록까지 포함한다. **실제 복원 확인은 EPIC 3에서 완료**한다.

## 5. EPIC 3 — 비용과 전체 손익, 기록 복원

**포함 Story: S3.1~S3.5, 총 5개**

기존 저장·계산·백업을 재사용해 비용을 연결한다. 비용 관리가 완성된 후 전체 손익을 확인하고, 모든 종류의 기록을 복원한다.

| Story | 사용자가 할 수 있는 일 | 자동 검사 | 화면에서 확인할 행동과 예상 결과 |
| --- | --- | --- | --- |
| **S3.1 비용 등록** | 날짜·항목·금액으로 비용을 기록한다. | 귀속일·금액 검사, 합의한 추가·대체 처리, 월 계획과의 이중 집계 방지 검사. | 비용을 입력해 저장한다. 해당 날짜의 비용 목록에 나타나고 다시 열어도 유지된다. |
| **S3.2 비용 수정** | 잘못 입력한 비용을 고친다. | 금액·귀속일 변경, 이전·새 기간 합계, 실패 시 기존 기록 유지 검사. | 비용 금액이나 날짜를 바꾼다. 같은 기록이 변경되며 날짜별 비용 합계에 반영된다. |
| **S3.3 비용 삭제** | 잘못된 비용 기록을 제거한다. | 대상만 제외, 삭제 취소·실패, 월 계획 자동 변경 방지 검사. | 삭제를 취소하면 유지되고 확정하면 사라진다. 재료 수량과 메뉴에서 남는 금액은 직접 바뀌지 않는다. |
| **S3.4 기간 전체 손익 확인** | 선택한 일·월의 매출·비용·손익을 확인한다. | 수수료·원가 이중 차감 방지, 운영비 포함, 메뉴 합계와 손익 일치, 미마감·누락·0매출 처리 검사. | 대시보드에서 일·월을 바꾸고 판매·비용을 변경한다. 손익이 같은 기록 기준으로 갱신된다. 2026년 9월은 18일까지의 자료임을 보여준다. |
| **S3.5 백업 복원** | 기록을 백업 시점으로 되돌린다. | 전체 자료·정책 일치, 깨진 파일·요약 파일·중복ID·미지원 버전 거절, 취소·적용 실패 시 전체 원본 유지 검사. | 백업 후 판매·비용·재고를 변경하고 복원한다. 파일 검사→대체 확인→실행 순서로 진행되며, 세 종류 기록과 수익성·손익·잔량이 백업 기준으로 돌아온다. |

### 완료 기준

판매 입력→메뉴 수익성→기간 손익·재료 잔량까지 연결된다. 비용 변경은 손익에 반영되고, 전체 백업·복원 후 동일한 기록과 계산 결과를 확인할 수 있다. 잘못된 복원 파일이나 실패한 처리로 기존 자료가 일부만 바뀌지 않아야 한다.

## 6. 최종 검사와 배포

배포는 새 Story가 아니라 EPIC 3의 최종 완료 작업에 포함한다.

- 자동 계산·저장·복원 검사와 코드 오류 검사, 배포 파일 생성을 통과한다.
- 실제 브라우저에서 종료·재접속, 입력 오류, 취소, 전체 백업·복원을 확인한다.
- TRD의 조회·저장·백업 처리 속도 목표를 제공 자료로 측정한다.
- GitHub에는 코드·문서·가상 샘플을 보관하고 실제 매장 기록·백업은 올리지 않는다.
- Vercel 운영 주소에서 전체 핵심 흐름을 다시 확인한다.

PRD의 **전체 4시간 목표**를 유지한다. 이 계획이 개발만 새로 4시간을 확보한다는 뜻은 아니다. 남은 시간을 확인하고, 부족하더라도 계산·저장·검사를 빼거나 가짜 동작으로 완료 처리하지 않는다.
